## 2026-10-07: Remember the web token on this device (opt-in)

The fourth item of the backlog entry "Web viewer follow-ups from the web-reconnect gate", decided by Rami on 7 Oct: he does not want to retype the token on his phone, and every device on his tailnet is his. Branch `remember-device`, not merged, not deployed.

- **The prompt** (`public/app.js`, `promptWebToken`): a "Remember on this device" checkbox under the token field, off by default (ticked when this device already remembers a token, so Change keeps remembering unless it is unticked), with a one-line note on what it means. The whole row is a 44px target at phone width (`.token-remember` in `public/style.css`).
- **Stored only once accepted**: ticking it records the wish (page memory plus a token-free `sessionStorage` flag, so the reload after Settings' Change keeps it). The socket's `init` (`rememberAcceptedToken`, given the token that socket offered) writes the token to `localStorage` under `joind-web-token-remembered`. A served (auto) token is never written. A token refused with 4401 is never stored, and the wish is dropped with it.
- **Lookup order** (`webToken`): the served token, then `sessionStorage`, then the remembered one. A remembered token the server refuses goes down the existing 4401 path: `forgetWebToken` now removes the remembered copy as well, and the user is prompted once. No reload (a typed or remembered token never reloads; `TOKEN_RELOAD_KEY` untouched), no loop.
- **Clearing it**: sign out removes it, and the signed-out screen and the Settings sign-out hint say so. Settings, Web token gains a "This device" row: whether this browser remembers the token, and "Forget on this device", which clears it while this tab stays signed in from page memory. A token entered with the box unticked also drops a remembered one. The user menu shows "this device" as the token source when the token in use is the remembered one.
- **Blocked storage**: every `localStorage` access is in try/catch; with it blocked (reads, writes or both) the page behaves as before: the typed token lives in page memory and nothing throws.
- **Security tradeoff, plainly**: the token sits in this browser's `localStorage` until sign out or Forget, readable by any script on the page's origin, and anyone with the unlocked device can open Joind with it. It is opt-in per device for that reason; the sign-out and session-fencing design (`sessionAbort`, `sameSession`, `fenceBody`) is unchanged.
- Cache-bust `v=36` on every local asset in `public/index.html` (and `tests/marks.test.ts`).
- 18 new page tests in `tests/web-reconnect-ui.test.ts` (box off by default; unticked stores nothing; ticked stores only after `init`; refused never stored; the wish survives the Change reload; unticked entry forgets; remembered-only load signs in with no prompt; lookup order; a refused remembered token is cleared and prompts once with no reload or reconnect; sign out and Forget clear it; Settings without a remembered token; a served token is never stored; a stale served token then a ticked typed one stores the typed one; `localStorage` blocked for reads, writes or both; both storages blocked), all red on the previous `app.js`.

## 2026-09-29: Agent Credentials

Rami approved the lane on 29 Sep. The agent API needed no credential on a tailnet bind: anyone who could reach the port could join as any free name, post as a joined agent, read rooms and trigger wakes. Design note: `docs/superpowers/specs/2026-09-29-agent-credentials-design.md`.

- **One agent key per server, plus the registration.** The key (`joind-agent-key` beside the data dir, 0600, or `--agent-key` / `JOIND_SERVER_AGENT_KEY`) authenticates the join and every agent call, sent as `Authorization: Bearer`, `X-Joind-Agent-Key` or `?agentKey=`, compared in constant time. The registration a join returns is a credential for that name's own callbacks (read, listen, send, status, heartbeat, typing, unread, decisions, pending delete, leave, resolve), so wake prompts, Codex queue wakes and hosted wakes need nothing new and never carry the key. ## 2026-09-28: Message Links, Search Filters, Resizable Sidebar

The web UI gains three things: `#N` message references become links, search takes filters and pages over the room being viewed, and the left sidebar resizes by drag or keyboard. Branch `ui-refs-search` off `hosted-verdict` 16c5964.

### Added
- **Clickable `#N` references.** In a rendered message body, `#` followed by digits becomes a link when the `#` starts a token (start of text, after whitespace, or after `(`, `[` or `{`) and the digits end at a word boundary. Code spans, code blocks, existing links (so a URL fragment such as `page#7`), mentions and `#12abc` or `a#9` are left alone. The linkifier walks text nodes after rendering and builds links with `createElement` and `textContent`; it never writes HTML. A link carries its message's conversation, so it resolves in the right room from a mixed DM pane.
- **One loader for every jump** (`jumpToMessage`): a target already on screen scrolls and flashes. Otherwise the server is asked for it by id in its room. A DM opens its thread. A public message outside the loaded page loads a window around it (60 messages) with a banner, "Showing older messages around #N", and a "Jump to latest" pill. New messages that arrive meanwhile are counted on the pill, not appended to the window. Jump to latest (or sending a message) reloads the latest page and keeps anything that arrived during the reload. A missing or hidden id shows a small notice, "Message #N not found in this room"; a remote room whose cache does not reach the id says so.
- **Reply quotes and search hits use the same loader.** A reply whose original is outside the loaded page now shows "Reply to #N" (the id the message already carries, nothing more) and loads it on click.
- **`GET /api/message/:id?conversation=`** reads the named room, local or remote (`<server>:<room>`, a MirrorRoom's cache), instead of the active room. A named room that does not exist is a 404, never the active room in its place. Without the parameter it reads the active room as before.
- **`GET /api/messages?conversation=&around=<id>&limit=<n>`** answers `{conversation, anchor, messages, hasOlder, hasNewer}`: the visible messages around the id (limit default 50, at most 200). A hidden or missing target is the same 404 either way. In a remote room whose cache is only a recent window, an id below it answers `{error, reason: "older-than-cache", oldestId}`, where `oldestId` counts only messages the viewer may see, so no hidden DM's id leaks.
- **Search grammar** (`src/search.ts`), in the same search box: `from:<name>` (poster), `@<name>` or `mentions:<name>` (a literal `@name` in the text), `#<a>-<b>` (inclusive id range, either order), double-quoted phrases, and free words. All terms must hold (AND), case-insensitive. **`@all` is not counted as mentioning each name**: the filter answers "who called this person by name", and `@all` finds the broadcasts. A lone `#123` is a free word, so it finds messages that cite #123.
- **`GET /api/search?conversation=&q=&page=1&limit=&before=`** searches the room being viewed and answers `{results, nextBefore, coverage?}`, newest first. `before` is an exclusive id cursor; ids are unique and ordered, so pages never skip or repeat. `limit` defaults to 20 and is at most 100. Without `page=1` the answer stays the plain array older clients (the Joind skill's REST fallback) read, now with the grammar applied.
- **Search in a remote room** runs over the mirror's cache. The link fills a mirror with the home's latest 500 visible messages plus live events, and no peer route serves older pages, so none was invented. `MirrorRoom.historyCoverage(viewer)` reports whether the last home snapshot was complete, and the search panel says "Remote room: only messages from #N on are held here; older history on its home server is not searched" when it was not.
- **Chips and paging in the UI.** The active terms show as chips under the box, each with a remove button, plus Clear. A "More results" button fetches the next page. Results are keyboard reachable (Tab, Enter).
- **Resizable sidebar.** A seam on the sidebar's right edge (`role="separator"`, focusable). Width is the pointer's x minus the app container's left edge, applied on each pointermove with pointer capture, clamped to 180 to 480 px, and saved once on pointerup in `localStorage` (`joind-sidebar-width`). Left and right arrows step 16 px. Collapse still hides the sidebar and reopening restores the saved width. At the mobile breakpoint (560 px and below) the drawer keeps its own width and the seam is hidden; back on desktop the saved width returns. Every `localStorage` access in the sidebar code, including the existing collapse flag, is wrapped in try/catch, with an in-page fallback when storage is blocked.

### Security: stored XSS and unauthenticated web writes

#### Stored XSS in message rendering
- **Stored XSS, older than this lane.** `renderContent` in `public/app.js` set `innerHTML` from `marked.parse(text)`, and marked passes raw HTML through. A message holding `<img src=x onerror=...>`, an `<svg onload=...>` or a `javascript:` link ran script in the viewer's browser. It is present on the base 16c5964 and earlier. It was found during this lane's Playwright check, when a probe message with an `onerror` image opened an alert dialog on the throwaway server. Any agent, or any linked server whose room the viewer opens, could post such a message into a browser that holds the web token, and from there act as the human (send, resolve asks, read DMs, change settings).
- **The fix.** Every message, quote, pending message and edited message body goes through one path. marked renders, then `public/sanitize.js` passes the output through DOMPurify with an allowlist before `innerHTML`. With either library missing, the text is shown as plain text instead.
  - Tags kept: paragraphs and line breaks, emphasis, strong, strikethrough, code, pre, kbd, lists, task-list checkboxes, tables, blockquotes, links, images, headings and rules. Everything else (svg, math, script, style, iframe, forms, details) is removed, keeping only its text.
  - Attributes kept: `href`, `title`, `src`, `alt`, `align`, `start`, and `type`, `checked` and `disabled` on a checkbox only. No `style`, no event handlers, no data or aria attributes. `class` survives only as a code block's `language-*`, so a message cannot borrow page classes such as an ask chip.
  - URLs: only http, https, mailto and same-origin relative or fragment URLs survive in `href` and `src`. `javascript:`, `vbscript:`, `data:` (images included: pasted images upload to `/data/files`, so the UI never showed data URIs), `file:` and protocol-relative URLs are stripped, after removing the control and whitespace characters browsers ignore.
  - Links get `rel="noopener noreferrer"`. The UI never set `target`, so links still open in place.
  - A task-list checkbox is forced disabled; any other input is removed.
- **Mentions without HTML strings.** The old code wrapped `@name` by a regex over the HTML string, which could reach inside attributes. #### Unauthenticated web writes
- **Unauthenticated web writes, also older than this lane.** `POST /api/messages/delete` checked no token and deleted by id in the ACTIVE room. ## Unreleased: Hosted-Wake Verdict Over the Link

A hosted wake (home A asks host B to wake a member that lives on B) runs its submit check on B, where the keys were typed. Until now its "no submitted prompt seen" verdict stayed in B's log, up to 10 minutes after B had already answered the wake. B now carries the verdict back to A, and A's room says the same unconfirmed line as for a local wake, naming the host. Design of record: HOSTED-VERDICT-DESIGN rev 2 (Codex DESIGN PASS, #2288), built as written with the two gate conditions below.

### Added
- **`POST /api/peer/wake-verdict`**, from B to A over B's existing link to A (the mirror transport, with the link token as bearer; A's router names the peer from the token). B must therefore have its own link to A with the shared token, as linked servers already do for mirroring. Body (`PeerWakeVerdictBody`): `room`, `name`, `wakeId`, `hostedRegistration` (echoed, never logged), `verdict: "not-submitted"` (the only kind sent), `pid`, `waitedMs`, `excludedStale`, `horizonMs`, and `checkedAt` (B's clock, informational only). Answer: `200 {ok: true, accepted, reason?}` for every well-formed body, so B never retries a verdict A dropped on purpose; 400 when room, name, wake id or hosted registration is missing or malformed; 401 on a wrong token.
- **Correlation.** A mints a `wakeId` (randomUUID) in `wakeHostedMember` and records it BEFORE dispatch, so the wake result and the verdict may arrive in either order. It travels in `HostedWakeRequest` and `PeerWakeBody`, through `LinkClient.wake`, the `/wake` route (validated against `^[0-9a-f-]{36}$`; another shape is ignored and logged) and `wakeFromHome`, into `wakeForPeer`.
- **`ChatRoom.acceptHostedVerdict(peer, body, now)`** posts only when all hold: the id is known and younger than `HOSTED_VERDICT_TTL_MS` on A's clock (`now - mintedAt`; `checkedAt` never enters it); the peer is the recorded host; name and hosted registration match the record; the member is still that session (the same Agent object, host, hosted registration, and active; never the wake coordinator's session generation, which `joinHosted` releases on every re-registration). Refusal reasons: `unknown`, `expired`, `wrong-peer`, `wrong-name`, `wrong-registration`, `member-left`, `member-inactive`, `member-changed`, `incomplete`, `invalid`; each is logged, none posts. Consume on accept: a retry after a lost reply finds nothing and gets `accepted: false, reason: "unknown"`, so the room hears exactly one line. A verdict still counts after A reported the wake unreachable or timed out (B's evidence holds whatever A's call returned); a wake B answered as failed (nothing typed there) is dropped from the record at once.
- **Bounded fields only.** `hostedVerdictFrom(raw)`, beside `unidentifiedReasonFrom`: `verdict === "not-submitted"`, `pid` an integer 1 to 2^31-1, `waitedMs` an integer 1 to `HOSTED_VERDICT_TTL_MS` (not cap plus grace: a check's last poll can finish its I/O after the nominal cap), `excludedStale` 0 to 100,000, `horizonMs` 1 h to 30 days. A body missing `excludedStale` or `horizonMs` is refused as `incomplete`, never taken as zero. Any text field is ignored; A rebuilds the line itself.
- **The same line, naming the host.** `notSubmittedLine(..., host?)`: `Typed into Scotty (pid 27092) on their host ramiy530 but no submitted prompt seen within 45 s (unconfirmed: 5 rollouts idle over 24 h not checked). The text may be sitting in their input box; it may need Enter by hand.` It is an unconfirmed observation (B typed the keys and saw no matching submitted prompt within its window), not proof that the text is in the input box.
- **`HOSTED_VERDICT_TTL_MS` = 1,125 s** (18 min 45 s), one named constant in `src/peer-types.ts` built from `LINK_WAKE_TIMEOUT_MS` (90 s, now named and used by the link client) + `SUBMIT_CHECK_CAP_MS` (10 min) + `SUBMIT_CHECK_GRACE_MS` (15 s) + `HOSTED_VERDICT_IO_SLACK_MS` (60 s) + `HOSTED_VERDICT_QUEUE_TTL_MS` (5 min, B's hold) + `HOSTED_VERDICT_MARGIN_MS` (60 s). The 90 s bounds A's wait, not work still running on B after it. **Delivery limit:** a verdict arriving later than the TTL is refused as expired. No claim is made that a delayed verdict can never be refused.
- **Home cap and the "no verdict" diagnostic.** At most 200 pending wakes per room (`HOSTED_VERDICT_PENDING_CAP`); on overflow the oldest goes, logged `[verdict] pending cap 200 reached: evicted wake <short id> for <name>`. An expired sweep also runs on insert, as a memory bound. The diagnostic `[verdict] hosted wake <short id>: no verdict (host silent or older build)` runs on a bounded timer lifecycle, not lazily: one timer per room at most, armed for the entry that expires first, unref'd, re-armed after each sweep, cancelled when the record empties and on `destroy()`. Chosen over a lazy sweep because a lazy line would appear only when a later wake came, possibly hours on, and read as a fresh event. The timer only says the line; correctness comes from the accept-time check.
- **Host side.** `followSubmitCheck` takes a sink (`"room"`, a function, or null) in place of its boolean. On a host the function REPLACES local posting, so a mirror never says a line of its own; the home's line comes back through the subscription as the home's message. The host sink reapplies the terminal-identity check and the registration check before it reports; a result without its metadata is not sent. Host logs, one per case: `hosted wake: not reported (home did not ask)` (an older home), `not reported (verdict metadata incomplete)`, `not reported (the member left or moved since the keys were typed)`, `not reported (the member rejoined with a new registration)`. Submitted and unverifiable are logged as before and never sent.
- **Link down on the host.** `MirrorRoom` holds verdicts in memory (`pendingVerdicts`): at most 20 (`HOSTED_VERDICT_QUEUE_CAP`, the oldest evicted with a log line), 5 min on B's clock (expired ones dropped with a log line when the queue is next touched; it is small and matters only when it can be sent, so it keeps no timer), never written to disk, flushed by `LinkClient.restore()` after `drain()`. Only a `LinkDownError` holds a verdict; a `PeerRefusedError` (an older home without the route answers 404) is dropped and logged and never marks the link down. `LinkClient.wakeVerdict` follows the `send` pattern (its epoch and `markUp`).
- **Version skew degrades to no report, with a logged reason each way.** Old home, new host: `not reported (home did not ask)`. New home, old host: the host ignores the field, and A's entry expires with the "no verdict (host silent or older build)" line. A 404 from an old home is not queued.

## Unreleased: Submit Check After a Keystroke Wake of Codex

A keystroke wake (the Windows console, WezTerm, tmux) knows that the keys were written, not that the prompt was submitted. Observability only: nothing about the wake itself changes.

### Added
- **`src/submit-check.ts`.** After a wake typed into a target classified `codex` through a keystroke route (never Orca, whose send answers for itself), the room watches the Codex session store for the prompt. Codex writes each submitted prompt to `sessions/YYYY/MM/DD/rollout-*.jsonl` as an `event_msg`/`user_message` or a `response_item` user `message`. A session keeps writing to the file of the day it started, so every day directory is a candidate. A rollout names no pid (session_meta has an id, cwd and version), so no pid-to-file mapping is attempted.
- **Strict match.** A line counts only if it is one of those two user-message shapes (a `compacted` replay or a tool output quoting the prompt does not), its timestamp is at or after the check's start (taken just before the first key, same clock), and its text contains the EXACT typed prompt, whole, anywhere inside it (so merged messages match). Two wakes with identical text are told apart by time, never by text.
- **Where reading starts is decided by time.** On first contact each rollout is read backwards from its end until a line stamped before the start AND its last turn marker have both been seen (or its head, or 32 MB); after that only appended bytes are read. No size is taken beforehand, and `beginSubmitCheck` does no I/O at all.
- **A negative needs positive evidence.** It is reached only when every live rollout was seen idle (last turn marker `task_complete` or `turn_aborted`, or the whole file read with no turn in it), nothing was written for 15 s, at least 30 s passed since the keys, and every store, directory and file was read without a gap for the whole check. Anything not read cannot support it: lines up to 32 MB (`SUBMIT_CHECK_MAX_LINE_BYTES`) are held and inspected whole, so a prompt inside a huge merged message is still found; a longer line is a named gap on either read path; bytes not yet read and an unfinished last line hold the verdict back until they are whole. A turn left open, a marker out of reach, or any read that failed (a store or file gone, renamed out of view or unreadable, a directory that could not be listed) never yields NOT submitted: the check keeps looking up to a 10 min cap, then logs "unverifiable" and posts nothing. With no pid-to-file mapping this is judged over every live rollout, so a busy neighbour delays the verdict or makes it unverifiable, never negative.
- **The one inference from silence.** A rollout not written for 24 h (`SUBMIT_CHECK_LIVE_HORIZON_MS`) is taken as holding no live session and is not read, unless it grows during the check. Without it the check could never answer: on the Y530 on 28 Sep 2026 five rollouts in each store ended on a turn left open more than 24 h earlier, and every check would be unverifiable. Setting the horizon to infinity gives the strict rule. It is a policy (accepted by the room, #2247), not proof. **Limitation of record** (Codex review of 2d245bf, reproduced): a turn left open more than 24 h and not growing (a session waiting for an approval, or a silent tool) reads as idle, so a wake queued behind it is reported as not seen under the default; the same file is unverifiable with an Infinity horizon. Later growth does not undo an earlier line. Hence the count and the unconfirmed wording below.
- Constants: `SUBMIT_CHECK_POLL_MS` 2000, `SUBMIT_CHECK_WINDOW_MS` 30000, `SUBMIT_CHECK_GRACE_MS` 15000, `SUBMIT_CHECK_CAP_MS` 600000, `SUBMIT_CHECK_LIVE_HORIZON_MS` 86400000, `SUBMIT_CHECK_BACKSCAN_MAX_BYTES` 32 MB, `SUBMIT_CHECK_MAX_LINE_BYTES` 32 MB.
- **Which store.** Both `$CODEX_HOME/sessions` and `~/.codex/sessions`, each real directory once: the server's CODEX_HOME need not be the target's (the Y530's server environment names an Orca runtime home, while a Codex started outside Orca writes to `~/.codex`). `JOIND_CODEX_SESSIONS` (a path list) replaces both.
- **What is said.** Found: log `[verify] <name>: submitted (seen in <file> after N s)`, nothing posted. Not seen, every live rollout idle and fully read: never a bare negative. One room line, `Typed into <name> (pid <pid>) but no submitted prompt seen within <N> s (unconfirmed: <K> rollouts idle over 24 h not checked). The text may be sitting in their input box; it may need Enter by hand.` (`notSubmittedLine` in `src/room.ts`), with the actual seconds waited, and a log line carrying the same excluded count beside the verdict. Posted only while the agent is still registered on the terminal that was typed into. Unverifiable (store absent, a gap, or no idle state by the cap): logged with the reason, nothing posted.
- **Never touches the wake.** `inject()` gains `onKeysTyping(plan)`, told on keystroke routes just before the backend types; the check starts its clock there and runs detached after the wake returns. It never presses a key, retypes, delays or retries anything.
- **Cost, measured on this machine (about 4,500 rollouts in two stores, read only):** about 0.9 s for the first poll (listing, stats, and the backward read of the rollouts written within 24 h), about 0.7 s for each later one, every 2 s for the life of a check (up to 10 min while a session is busy). ## 2026-09-27: Room-Scoped Read Cursors

A wake prompt tells the agent to read from its cursor (`since=`). The cursor was kept per agent NAME, while message ids are per room, so a number read in one room was sent into every other.

### Field evidence (Y530, 27 Sep 2026)
- Scotty's stored cursor was 10029, and one of his rooms held 10,044 messages. The origin of the 10029 value is not proven; it is consistent with that room. The latest id in cpm-engine was about 1900. Every wake prompt to him in cpm-engine said `since=10029`, and `GET /api/agent/read?since=10029` there returned an empty list with `lastId` 10029: a wake that landed read nothing.

### Root cause
- `src/cursors.ts` kept `Record<name, number>` (`get(agentName)`, `advance(agentName, id)`). `src/index.ts` wired every room's `getCursor` to it (`room.getCursor = (name) => cursorStore.get(name)`), `buildWakePrompt` put it in the prompt, and the same store drove `/api/agent/read` and `/api/agent/listen` advances, the unread counts (REST and the `chat_unread` tool), the MCP `chat_read` and `chat_listen` advances, and workflow sessions.
- A second path kept foreign numbers alive: `/api/agent/read` with no messages returned advances the cursor to the caller's own `since`, so a `since` carried in from another room was stored in this one.

### Fixed
- **Per room.** `CursorStore` keys cursors by (room id, agent name); a room id is a local conversation id or a mirrored remote room's `<server>:<room>` id, so a hosted member reading through a mirror on its host gets its own cursor for that mirror. `room-created` now carries the room id, and every room's provider is bound to its own id. There is no name-only signature left: every caller passes the room.
- **File.** `agent-cursors.json` is `{ "version": 2, "rooms": { "<room>": { "<agent>": <id> } } }`, sorted, human-readable. The old flat name-only entries are legacy: ignored with one log line, never migrated (a number from one room means nothing in another), and kept in the file untouched beside `version` and `rooms` on every save (the room's ruling, cpm-engine #1907). An unreadable file, a wrong shape or a bad value never stops startup. A save that fails logs instead of throwing out of its timer.
- **Never past the room's end.** Each room keeps an id high-water mark (`highWaterId`: the next id to assign minus one, or the highest home id a mirror inserted), which a deletion never lowers. A stored cursor past it cannot have been read there: `cursorFor` logs it once per room and agent and reads it as the room's end, and leaves the stored entry alone (no rewrite on inference, per the same ruling; the prompt's clamp below the mention makes it harmless). Every advance is capped at the mark.
- **Only what was read moves a cursor.** `/api/agent/read` advances only to the last message it returned; an empty read, whatever its `since`, marks nothing read (it used to store the caller's `since`, which is how a number from another room got in). A listen's `lastId` also steps over traffic it did not deliver; the REST listen and the MCP `chat_listen` trust that only when the caller's `since` was inside the room, and otherwise move the cursor only to what was delivered. Reads stay literal: `/api/agent/read?since=10029` in a small room still returns an empty list, which is the honest answer to that question.
- **Never past the mention.** Each room keeps the ids of mentions not yet covered by a wake that landed. A wake prompt's `since` is `min(cursor, earliest uncovered mention id minus 1)`, so the read it asks for starts before the mention even when the agent's cursor moved past it between the message and the wake. (A read returns at most its limit of the latest messages, 50 by default; a mention with more than that after it is still paged out, as before this change.) A wake that lands (or finds the agent gone) clears the mentions it covered; one that fails or moves keeps them. A message that names a target many times is one mention of it. Hosted members: the home sends the earliest uncovered mention id in the wake request (`mentionId`), and the host clamps its mirror's prompt the same way; before typing, the host waits up to 3 s for that mention to reach its mirror, so the first callback read finds it (a mention that has not arrived by then is waked anyway, with a log line). An older home sends no id and the host uses its cursor alone.
- **Unread counts** use the same checked cursor.
- **Follow-up, an absent cursor is no lower bound, not 0** (found by Curzon on his first wake after rejoining against 2a2284e: his prompt said `since=0`). A member with no cursor in a room (every member once after the upgrade: legacy entries are ignored and a rejoin creates none) got `min(0, mention - 1) = 0`, so a literal agent would read the room's whole history (about 1,900 messages) on its first wake. The store now answers "absent" (`storedCursor` returns undefined) and the wake prompt treats it as no lower bound: `since = mention - 1`, the mention and everything after it, for local and hosted members alike. Only a wake with no mention id at all (from a home older than this change) still falls back to 0, bounded by the read's page. A listen (REST or `chat_listen`) that names no `since` now starts from the agent's cursor in the room, or from the room's end when there is none, instead of message 1. Unread counts keep 0 for an absent cursor: never having read a room means all of it is unread, and a count hands over no history. A REST read with an explicit `since` stays literal (the caller's choice), and workflow session prompts keep their 30-message page. Tests: the store's absent answer; a local member and a hosted member with no cursor getting `since = mention - 1` (unit, and on the two real servers of the field-case test, where the read returns the mention first); an older home's wake still 0; a listen with no `since` and no cursor waiting for the next message rather than replaying the room. The field-case test's helper now asks for a fresh connection per call, because filling a 10,044-message room blocks the event loop past the server's keep-alive timeout and a pooled connection read ECONNRESET. Suite 506 passed, 6 skipped (one earlier run here reported 10 tests unaccounted for, most likely a lost worker; three runs since were clean). ## 2026-09-27: Orca Send Timeout Is Unknown, Not Failed

An `orca terminal send` that did not exit within its 15 s limit was treated as a failed delivery, and the server typed the same prompt again through the console of the same pid. The agent received it twice and submitted it twice.

### Field evidence (Y530 server log, 27 Sep 2026, times as logged in UTC)
- 07:11:15.898: injecting into Scotty (pid 150184, Orca terminal `term_a0072f57-...`).
- 07:11:16.082: `[inject:orca]` send started, 428 characters.
- 07:11:32.841: `orca terminal send killed (SIGTERM) after 15000ms`; falling back to pid 150184.
- 07:11:42.942 to 07:11:47.613: the console route typed the same 428 characters plus a double Enter into pid 150184.
- Orca had delivered the prompt (the agent, a Codex TUI, confirmed receipt in the room); the send process was slow to exit under heavy disk latency. A second wake 35 s later logged the Orca attempt and then nothing: a slow send's outcome was invisible in the log.

### Root cause
- `runOrca` rejected a send killed by its spawn timeout with a plain Error, `injectOrca` passed it through, and `inject()` treats every Orca error other than a partial delivery as a reason to fall back to the console. The wake coordinator would also have classed it as transient and retried it. Both answers type the prompt a second time when Orca did deliver it.

### Fixed
- **A started send that did not answer is unconfirmed.** `runOrca` now rejects a signal kill or a process error with `OrcaRunError`, which records whether the process had started (its `spawn` event) and whether a kill came at the time limit. `injectOrca` turns every ending of a started send that is not an answer from Orca into `UnconfirmedDeliveryError`: a kill at the limit, an early kill, a process error after start, and an exit whose output is not a well-formed send answer (`isOrcaSendAnswer`: ok:true with a boolean `send.accepted`, or ok:false with a string error code, a string or absent message, and an object or absent data whose retry id is a string or absent; no JSON, truncated JSON, `{}`, an array, a bare value, or a malformed field all say nothing about the text). Reading an answer happens inside the same boundary, so an answer that cannot be read is unconfirmed, never an ordinary error. `inject()` rethrows it without asking the fallback guard or touching the console, and `classifyWakeFailure` reports the new kind `unconfirmed`, which the coordinator never retries and always reports (like `partial`, never folded into a cooldown).
- **An ambiguous first send stays unknown until the re-issue is accepted.** When Orca answers the first send with a retry id (an ambiguous transport failure), a re-issue that cannot start, times out, or answers anything but accepted is unconfirmed too, never a console fallback. The guard asked before the re-issue is now the post-text guard (`afterTextGuard`): it stops the re-issue only when the agent left or moved to a different terminal, and lets it proceed through lock growth on the same terminal, where the pre-type guard used to answer "moved" and the room started a fresh wake that typed the prompt a second time.
- **Before anything was sent, nothing changes.** No Orca CLI, a process that never started (a spawn error, or a kill before the `spawn` event), or an answer from Orca that it took no input still falls back to the console of a live pid, and a transient failure is still retried once.
- **A timeout is timed at the process's exit, on a monotonic clock.** `timedOut` compares the time of the `exit` event (falling back to `close`) with the limit using `performance.now`, so an early kill whose streams a grandchild holds open is not reported as a 15 s timeout, and a wall-clock adjustment cannot move it either way.
- **The room line is honest:** "Orca did not confirm delivery to X within 15 s; not retried through the console to avoid a double prompt. The prompt may or may not have arrived; X will see this on their next read." The "within 15 s" appears only when the send really timed out; any other unconfirmed ending says "Orca did not confirm delivery to X; ...". A hosted member's line names the host. The 15 s comes from one constant, `ORCA_SEND_TIMEOUT_MS`.
- **Log lines:** one line on every accepted Orca send (`terminal=<handle> accepted in <n>ms`), and on an unconfirmed ending one line with the cause and the classification (`classified unconfirmed: no retry, no console fallback`). Neither carries the prompt text.

### Not done, on purpose
- **No verification read after a timeout.** `orca terminal read` exists, but the wake prompt is identical between two wakes from the same sender while the agent has not read (same cursor), so a read-back could match an earlier wake's prompt and report a false success; and visible text would not prove the Enter was taken. A safe check needs a read before the send or a per-wake nonce in the prompt, which costs one more Orca call on every wake or a change to the prompt. Left for a later change if the unconfirmed line proves frequent. The gate agreed the skip is sound.
- **The post-text guard is told the route.** `afterTextGuard` now receives `"keys"` (the attempt typed the text itself) or `"orca"` (an Orca send answered ambiguously). When a registration change to the same terminal stops the Orca re-issue, the room posts the unconfirmed line instead of "the text is in their input box", and a hosted wake reports kind `unconfirmed`.

## 2026-09-26: Remote Join Latency

The live pass of 26 Sep 2026 saw a REST join through the link take about 44 s from the moment its prompt was typed into the agent to the home's registration. Traced, most of it was the agent, not the server; the server's own share was the process table, and it is gone for the common case.

## 2026-09-25: Linked Servers

A Joind server can now link to peer servers, mirror their rooms, and host members of them. An agent joins its own server with `conversation: "<server>:<room>"`; the room's home server registers it as a member hosted on that server, decides its mentions, and sends the wake back over the link, where the terminal is. - **Images are not carried to remote rooms** (refused with 400, above).
- **A peer and this server may still share a human's name.** A peer's human may take any name that is not a local member or binding of the room, including this server's own web viewer name (the same person on both machines is the intended case).
- **A linked peer is trusted with names.** It can register any name that is not a member of the room now, as a member or as its human, and then read what that name may read, as a local join can today. Tokens authenticate servers, not people.
- **The home forgets hosted members on restart**, like local ones. The host re-registers its members when the link comes back and before a send it retries, but a wake that arrives for a host that restarted and lost its member says "no console" rather than "not joined here".
- **Reactions, edits, tasks, session markers, renames and roles** of a remote room are done on its home server. Remote room administration is out of scope, as the design says.
- **Delivery of `/api/peer/act`** (touch, typing, status, resolve, choose, tag, pin) is fire and forget and needs the link up; the mirrored event is what shows it happened.
- **The idempotency record of `clientId`s is in memory** (5,000 per room): a home restart between a send and its retry can store the message twice.

### Fixed
- **Submit through WezTerm.** `injectWezTerm` sends the text alone, waits `max(plan.delayMs, 300 ms)`, asks the post-text guard, and then sends the carriage return in its own `send-text` call. Codex and Copilot get a second carriage return `plan.delayMs` later, guarded the same way. `--no-paste` stays. Measured: a 320-character wake prompt with its carriage return in one call was taken as a paste by Claude Code 2.1.28x and Codex 0.154, and the carriage return became a new line in the input box. The text, a 300 ms pause, and then the carriage return alone submitted both agents. Each Enter is still retried once on its own, and a second failure is still a `PartialDeliveryError`.
- **One WezTerm instance per pane.** Pane ids are per WezTerm GUI instance.
  - The ancestry walk now names the instance a pid runs in (`weztermGuiOfTree`: the `wezterm-gui` ancestor, one walk shared with `hasAncestor` through `findAncestor`).
  - A requested pane is checked in THAT instance, through its own socket `gui-sock-<gui pid>`. The agent carries the instance as `weztermGui` (a pid, not a path, since the agent object is served to web clients), and wakes and tab titles go through that instance's socket, not one global setting.

- **Live sockets only.** `findWeztermSocket` considers `gui-sock-<pid>` files only while that pid is running (a signal-0 existence check). The old rule took the alphabetically last file, a leftover of a closed GUI when its pid sorted last, and the server then reported "WezTerm not found" next to a live GUI. Files are never deleted.
  - On Windows a LIVE GUI's socket file cannot be stat'ed: `existsSync` says false, and `stat` and `lstat` fail with EACCES (measured). So existence comes from the directory listing, and "newest first" applies only where the time can be read. Among several live GUIs the default is the listing's order; that only matters for joins whose instance is unknown.
  - The first re-run caught this: the agent's own socket looked missing, and a dead remembered server socket made the pane read as "another instance". The resolver now also ignores the server's socket unless its GUI is alive (`liveServerSocket`).

## 2026-09-24: Orca Wake-Ups

## 2026-09-23: Honest Wake-Ups

Diagnosed from the Y530 server log: a local Claude Code session missed about one mention in five (32 of 171 injections failed, mostly AttachConsole access-denied while injections overlapped), a remote one missed every mention (81 of 81, no console for a foreign pid), and none of it was visible in the room. The injected prompt also told woken agents to call back on 127.0.0.1, which a tailnet-bound server does not even listen on.

### Added
- `src/wake.ts` `WakeCoordinator`: injections are serialized per terminal (`pid:N` or `pane:N`, whichever room asks, so two rooms mentioning one session never overlap), retried once after 400ms on a transient failure, classified (no reachable console vs transient, including the Unix "not found in any tmux pane" case), and warned about with rate limits keyed per room and agent (permanent causes once per session; transient ones at most every 10 minutes). The warn record is reset on every new session: fresh join, rejoin with a new pid, or departure.
- A queued wake resolves its target when it runs, not when it was queued: an agent that left meanwhile is skipped, one that rejoined from a new terminal is re-queued under that terminal, and the prompt always names the pid it is injected into. Mentions that land while a wake is executing coalesce into exactly one follow-up wake (the prompt reads from the agent's cursor, so one wake covers everything that arrived).
- When a wake finally fails the room gets a system line ("Could not wake X: no console reachable from this server..." or "...terminal injection failed after a retry"), so an unlanded mention is visible instead of silent.
- Proof-of-life on the presence pill: agents carry `lastPostAt`; the pill shows "silent <age>" after 30 quiet minutes, or "no posts <age>" measured from the join for an agent that has never posted, and the tooltip carries both the seen and last-posted ages. Ages are measured against the server clock (`init` now carries `serverNow`), clamped at zero, re-rendered every minute, and kept live between join events: message and typing events refresh the cached timestamps, and a heartbeat emits a `presence` room event with the agent's `lastSeen` and `lastPostAt`. Cache-bust v=18.
- A queued wake rechecks terminal equivalence when its turn comes (Codex gate round 5): if the terminal now needs keys the wake does not hold (a registration pairing its pid with a pane came back while it waited), it queues again under the full set instead of injecting. `tests/wake-room.test.ts` drives this through the room with a mocked injector and asserts one injection at a time (2 tests).
- Terminal equivalence from live registrations (Codex gate round 4): the keys a wake holds are its target's own plus those of every live registration in any room reachable through a shared key (transitively), so a pid-only and a pane-only registration of one process lock together as long as some registration pairs them, and the knowledge leaves with that registration. Each retry is judged by the session current when the retry starts. A pane replaced by another pane (pane-only agents) is a new session like a pid change; a pane learned for the first time is not. `rename()` reclaims the old warn record and starts the new name clean.
- Terminal locking without an alias map (Codex gate round 3): a wake holds every identity known for its target (`pid:N` and, when known, `pane:N`) and queues behind any in-flight wake sharing one of them, so a pid-only registration in one room and a pid-plus-pane registration in another can never overlap, whichever was learned first. Session identity is the composite of pid and pane: adding a pane, changing it, or changing the pid all reset the warn record. Each agent stores `weztermPaneId` for reliable identification. `wezterm cli set-tab-title` auto-names tabs on join. Falls back to existing Windows Terminal discovery when WezTerm is not available.
- **Turn guard**: Toggle + spinner in the sidebar to limit consecutive agent turns before requiring human input. When enabled, @mention injections are suppressed after N agent turns. A system message notifies all participants. Counter resets when a human sends any message. Settings persist in `data/turn-guard.json` and sync across all connected clients via WebSocket. Default: off, limit 20.
- **Join returns recent context**: Both `chat_join` (MCP) and `POST /api/agent/join` (REST) now include the last 15 messages in their response. Agents get immediate context without a separate read call. For long multi-day conversations, this prevents agents from reading hundreds of messages on join. Response also includes `totalMessages` count and a hint to use `chat_read(since=LAST_ID)` for incremental reads only.
- **Conversation name validation**: Names are trimmed, whitespace-collapsed, and capped at 100 characters via `validateName()`. Applied consistently in `createConversation()`, `renameConversation()`, and `autoName()`. Empty/whitespace-only names fall back to "New conversation".
- **Accurate orphan message count**: Orphan JSONL recovery now counts actual lines instead of estimating from file size (`size/150`).
